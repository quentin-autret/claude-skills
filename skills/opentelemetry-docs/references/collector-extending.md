## Distributions

- Official distributions: Core, Contrib, Kubernetes (`otelcol-k8s`), OTLP (`otelcol-otlp`), eBPF Profiling, each defined by its `manifest.yaml`. https://opentelemetry.io/docs/collector/distributions/
- Third-party distributions (ADOT, Grafana Alloy, Splunk, Elastic EDOT, Datadog DDOT) are not validated or endorsed by OpenTelemetry. https://opentelemetry.io/docs/collector/distributions/#third-party-distributions
- Default: build your own distribution with only the components you use, which shrinks the attack surface; keep the option to switch to Contrib. https://opentelemetry.io/docs/security/config-best-practices/#minimize-the-number-of-components , https://opentelemetry.io/docs/guidance/reference-implementations/adobe/#custom-distribution-and-components
- `otelcol components` lists what a binary contains and each component's stability. https://opentelemetry.io/docs/collector/troubleshooting/#check-collector-components

## Building with ocb

- `ocb` (OpenTelemetry Collector Builder) comes from releases tagged `cmd/builder`, or Homebrew tap `open-telemetry/tap`. Needs a Go version compatible with the Collector release. https://opentelemetry.io/docs/collector/extend/ocb/#install-the-opentelemetry-collector-builder
- `dist.output_path` defaults to a random temp directory: always set it. Other defaults: `name` `otelcol-custom`, `version` `1.0.0`. https://opentelemetry.io/docs/collector/extend/ocb/#configure-the-opentelemetry-collector-builder
- The docs example lists `providers` (env, file, http, https, yaml); list the ones you need. In the example, components all use one 0.x version and confmap providers use a v1.x version. https://opentelemetry.io/docs/collector/extend/ocb/

```yaml
dist:
  name: otelcol-dev
  output_path: ./otelcol-dev
exporters:
  - gomod: go.opentelemetry.io/collector/exporter/otlpexporter v0.159.0
receivers:
  - gomod: go.opentelemetry.io/collector/receiver/otlpreceiver v0.159.0
providers:
  - gomod: go.opentelemetry.io/collector/confmap/provider/envprovider v1.48.0
  - gomod: go.opentelemetry.io/collector/confmap/provider/fileprovider v1.48.0
```

https://opentelemetry.io/docs/collector/extend/ocb/#configure-the-opentelemetry-collector-builder

- Build with `./ocb --config builder-config.yaml`. Find module paths and versions in the Registry (Collector filter). https://opentelemetry.io/docs/collector/extend/ocb/#generate-the-code-and-build-your-collector-distribution
- Containerize with a multi-stage build that runs the builder inside the image (binary matches the target arch), a distroless final stage and a non-root `USER`. The Dockerfile hardcodes `otelcol-dev` in `COPY` and `ENTRYPOINT`: update both if you rename the dist. https://opentelemetry.io/docs/collector/extend/ocb/#containerize-your-collector-distribution
- `components.go` is generated by the builder and headed "DO NOT EDIT", yet the receiver tutorial registers its factory by editing it by hand (adding it to the `factories` map). https://opentelemetry.io/docs/collector/extend/custom-component/receiver/

## Writing components

- One Go module per component; use Go workspaces (`go work use`) to develop it with a distribution. https://opentelemetry.io/docs/collector/extend/custom-component/receiver/#setting-up-go-module
- Factory: `receiver.NewFactory(component.MustNewType("tailtracer"), createDefaultConfig, receiver.WithTraces(createTracesReceiver, component.StabilityLevelAlpha))`. The stability level you declare is logged at startup (for example "Alpha component. May change in the future." at debug level): declare it honestly. https://opentelemetry.io/docs/collector/extend/custom-component/receiver/
- Config struct: an exported field per setting and a `Validate()` method returning an error on bad values. https://opentelemetry.io/docs/collector/extend/custom-component/receiver/
- `Start(ctx, host)`: the docs recommend a long-running receiver ignore the ctx passed to `Start`, create its own context from `context.Background()` with a cancel func, and cancel it in `Shutdown`. https://opentelemetry.io/docs/collector/extend/custom-component/receiver/
- Validate behavior with Go unit tests (consume path, capabilities, default config, validation). https://opentelemetry.io/docs/collector/extend/custom-component/connector/

## Connectors instead of signal-converting processors

- Processors that exported into another pipeline (`spanmetrics`, `servicegraph`) are deprecated; use the spanmetrics and servicegraph connectors. The routing processor is replaced by the routing connector. https://opentelemetry.io/docs/collector/extend/custom-component/connector/#why-use-a-connector , https://opentelemetry.io/docs/guidance/reference-implementations/adobe/#navigating-component-deprecations
- Connector factory: `connector.NewFactory(Type, createDefaultConfig, connector.WithTracesToMetrics(create, component.StabilityLevelAlpha))`; one factory can register several signal pairs. The create function receives the next consumer for the output signal. https://opentelemetry.io/docs/collector/extend/custom-component/connector/

## Authenticators

- Server authenticators intercept requests at receivers; client authenticators add credentials at exporters (an `http.RoundTripper` or gRPC `PerRPCCredentials`). One extension may do both. https://opentelemetry.io/docs/collector/extend/custom-component/extension/authenticator/#architecture
- `Authenticate` runs for every request and blocks the pipeline: keep it fast, honor context deadlines, set up keys and caches in `Start`, and emit metrics on auth errors. https://opentelemetry.io/docs/collector/extend/custom-component/extension/authenticator/#server-authenticators
- A custom authenticator must be compiled into the binary (ocb distribution, or a published Go module others add). https://opentelemetry.io/docs/collector/extend/custom-component/extension/authenticator/#add-your-custom-authenticator-to-a-distribution

## Remote management with OpAMP

- OpAMP is the open agent management protocol (HTTP or WebSocket). The OpAMP Supervisor runs the Collector and applies remote config. The built-in OpAMP extension only reports status, health and capabilities. https://opentelemetry.io/docs/collector/management/#opamp , https://opentelemetry.io/docs/guidance/blueprints/instrumenting-applications-and-processes-on-nonk8s-environments/#2-stand-up-an-opamp-management-plane-for-agents
- The OpAMP spec is Beta: evaluate implementation maturity, or fall back to configuration management and golden images. https://opentelemetry.io/docs/guidance/blueprints/instrumenting-applications-and-processes-on-nonk8s-environments/
- Supervisor binary from releases tagged `cmd/opampsupervisor`; manage the Contrib distribution. The docs' `tls.insecure_skip_verify: true` is demo-only. https://opentelemetry.io/docs/collector/management/#step-4---create-an-opamp-supervisor-configuration-file

```yaml
server:
  endpoint: wss://127.0.0.1:4320/v1/opamp
capabilities:
  accepts_remote_config: true
  reports_effective_config: true
  reports_health: true
agent:
  executable: $OTEL_COLLECTOR_BINARY
storage:
  directory: ./storage
```

https://opentelemetry.io/docs/collector/management/#step-4---create-an-opamp-supervisor-configuration-file
